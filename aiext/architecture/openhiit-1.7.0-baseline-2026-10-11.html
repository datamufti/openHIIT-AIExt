OpenHIIT Architecture Baseline

How upstream OpenHIIT was put together before this fork changed anything: which parts talk to each other, how a Timer turns into Intervals, what happens while one runs, and what gets stored. A frozen snapshot: don't edit it as the code changes; add a new dated baseline instead.

At a glance

Framework
Flutter (Dart). Builds for Android, iOS, web, Linux, macOS and Windows.
Size
73 Dart files, about 6,700 lines in lib/.
State
provider package: four ChangeNotifier providers.
Storage
SQLite file core1.db (schema v8) plus SharedPreferences.
Timer engine
background_hiit_timer 1.2.3, a separate package by the upstream author.
Tests
8 end-to-end integration tests. No unit tests.

The code is organised by feature. lib/features/ has one folder per screen (home, edit_timer, run_timer, settings, import_export_timers, reorder_timers, whats_new). lib/core/ holds what the screens share: models, providers, the database layer and the Interval calculation.

1. The big picture

Most of the app is a plain screens → providers → repositories → database stack. The exception is the running Timer. Its clock runs in a separate background process owned by the timer package, and the app only sees the result.

2. How a Timer becomes Intervals

A saved Timer stores settings: a list of activity names, work, rest and break times, warmup, cooldown and a repeat count. It does not store a list of segments. One pure function, generateIntervalsFromTimer, expands those settings into the ordered Intervals the engine plays. Saving, starting and the preview all call it, so it is the one place that defines what a workout looks like.

The code has no separate field for an Interval's type. Colours, "is this work?" and the sound rules all compare the Interval's name to strings such as "Rest" and "Break". An activity named "Rest" would be coloured and counted as rest. This matters for the AI generator, which will be producing names.

3. What happens while a Timer runs

This is the part a plugin system finds hardest. The run screen doesn't own the clock. It starts a background service (an Android foreground service, so the workout keeps going with the screen off), sends commands to it, and redraws from whatever snapshot arrives.

  • Pause, skip and restart take different routes. Pause goes through a SharedPreferences flag that the service re-reads every tick. Skip and restart are messages to the service. The screen also keeps its own copy of the paused state.
  • The run screen is required. Leaving it stops the service, so nothing can run a Timer without that screen open.
  • The Intervals can't change mid-run. They are copied into the engine's database at start. Changing them means restarting the service with a new list.
  • Time is counted in ticks. Elapsed time is 100 ms per tick, not a real clock, so a late tick stretches the workout slightly.
  • The finish callback is never called. The package declares onFinished but never calls it. Completion is the screen noticing that the status is "End".

4. What gets stored, and what gets shared

A Timer lives in three places with three different shapes: in memory as TimerType, on the device across four tables, and in export files as JSON. The Intervals are stored too, but they're always derived from the settings, so export leaves them out and import rebuilds them.

5. Also worth knowing

  • There's already a finish moment. The completion panel plays the end sound and fires 10 seconds of confetti. The "peak moment" work would change this rather than build it from scratch.
  • A Timer can only start from the editor. The only code that opens the run screen is the editor's Start button.
  • One screen is unused. ListIntervals is defined but nothing opens it.
  • Upstream is quiet. The last upstream change to lib/ was on 25 May 2026. Since then upstream has only merged dependency and CI updates.
